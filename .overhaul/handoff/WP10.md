  string field in a block other than `android` is checked against its `max` and the `rules` pattern its `rule`

  `android` keeps its own rule module because its checks span fields (min/target/compile SDK).

### Events the client sends

`POST /api/v1/events` with `Content-Type: application/json`, `X-Client: android-base-web/<build>` and
`{"session_id": "<uuid v4>", "events": [...]}`, batched (≤ 20 events, ≤ 8 KB), flushed 1.5 s after the first queued
event and whenever the page is hidden (`keepalive`).

| Event | When | Payload |
|---|---|---|
| `landed` | once per tab (a reload does not repeat it) | `returning` (a draft was in localStorage at load), `viewport` (xs < 480 ≤ sm < 768 ≤ md < 1024 ≤ lg < 1440 ≤ xl), `referrer` (origin only, omitted when it is the site's own), `utm_source`/`utm_medium`/`utm_campaign` (trimmed, ≤ 64) |
| `step_viewed` | each change of step (a reload shows `platform` again; another platform card or a restored draft is not another view) | `target`, `step` ∈ platform, identity, features, look, motion, build, review |
| `platform_selected` | leaving the platform step, including with the default kept | `target` |
| `preset_chosen` | a preset chip picked | `target`, `preset` |
| `generate_clicked` | Generate pressed with no validation errors | `target` |
| `download_started` | the generate response arrived OK, before the zip is saved | `target` |

The generate call sends `X-Session-Id` (the same id), `X-Config-Ms` (ms from the first `identity` view since load or
since Start over, to the click, rounded, clamped to 0…7 200 000, omitted when the identity step was not viewed) and
`X-Client`. Uncaught errors and rejections on any page, `/admin` included and from before hydration, go to
`POST /api/v1/client-error` as `{message (≤ 1000), stack (≤ 8000), url: origin + path, release: <build>}`, at most
five distinct messages per page.

Recorded end to end (below): every event above landed in `events`, `generated`/`downloaded` carried the session and
`config_ms`, the visit carried browser/OS/device/viewport, the generation row had `client = web` and the session.

## Deviations from MASTER-PLAN, with evidence

1. **Schema-1 cases are not run by the website's parity test.** The one case without `schema` (`schema 1 with flat
   android fields`, features `room`, `crashlytics`) is valid only because the generator renames legacy feature keys
   from its manifest (`firebase.legacy`), which the catalogue does not carry. The site only ever writes schema 2
   (`request.ts`), so the TypeScript validator reads schema 2 and the test filters on `"schema" in spec`; Python's own
   test still runs every case. Adding `legacy` to catalogue features (WP01/WP13 territory) would let the site read
   schema 1 too; nothing on the site needs it.
2. **BrandTint surfaces keep the template accent's tint.** The catalogue's palettes are resolved with the template
   brand, and `tokens` carries the result, not the tone `mix` table, so the Social preview cannot re-tint
   `background`, `surfaceVariant`, `border`, `divider` and `skeleton` toward a custom accent. Every brand role
   (accent, pressed, subtle, on-colours and the readable `*Content` shades) is recomputed. Fix belongs in
   `generator/genkit/tokens/web.py` (WP03): emit each tone's `mix` amounts and the untinted roles; the site would then
   apply them with an Oklab lerp ported from `brand.lerp_oklab`. Recorded under preview limitations too.
3. **The report button moved from a floating pill into the navigation.** The click-through showed the floating
   button covering Next and Generate at every width; the audit offered "hide it, or move it into the Nav". It reads
   the configurator's answers through a registered reader (`features/feedback/context.ts`).
4. **Not literally "one client island".** The configurator is the one stateful island (no landing re-render per
   keystroke, F10), but the theme toggle, the report button and the styles showcase are small client components of
   their own; each holds only its own state.
5. **`next/font/google` fetches the three site families from Google at build time** (it self-hosts them in the
   build output). That is the plan's choice (F12); a build without network fails at that step.
6. **The Python `\d` in `version_name` matches non-ASCII digits; JavaScript's does not.** The site is stricter for
   such input, never looser. No fixture case covers it.
7. **Unticking what the design style needs switches the style to the target's default.** The plan says only that a
   style's `requires` are turned on with it. Keeping the feature on would make the untick do nothing, and leaving it
   off would leave Glass without `liquidglass`, which `validateSpec` refuses on Review. Switching the style mirrors
   how an untick takes its dependents, the hint says so and Undo restores both (`07dd437`, `state.test.ts`).
8. **The admin's filter bar sticks only from `lg` (1024 px).** The fifth review asked for scroll padding under it;
   below `lg` its controls wrap to five rows, 230 px at 375 px wide, a third of a phone screen held over every panel
   (and most of it in landscape). It scrolls away there; from `lg` it sticks and the page's scroll padding follows its
   height (`16eb706`).
9. **Below `md` the nav's report and GitHub links are icons, and below 360 px the Beta badge is hidden** (`16edca2`).
   The fifth review offered either; both were needed to fit 320 px with 16 px gutters. The hero still says "This is
   beta.", and the icons keep their names for assistive tech and as a `title` (`1cd5aa6`).
10. **Compose Multiplatform is a "Coming soon" card, not a selectable beta, and the site names platforms the catalogue
    lacks.** A10.4 and step 3 draw multiplatform as a beta card with its `status_note`; REQUIREMENTS 36 (Oct 14,
    later, so it wins) has the site offer Android alone until phase B. The catalogue cannot carry that: the generator
    holds the multiplatform target as beta for its CLI, and WP07-A may merge before the Android release. So the site
    keeps its own `OFFERED` set and `ANNOUNCED` titles (`lib/catalogue.ts`, `ddc533f`); the beta card, its status note
    and the "Not in this version" list come back when phase B adds `multiplatform` to `OFFERED`.

## Rules and gotchas the docs must state

- The website builds from `web/frontend/lib/catalogue.json`. After changing a feature, preset, token, field or rule:
  `python3 -m genkit.core.catalogue --write` (or `npm run catalogue` in `web/frontend`) and commit the file; CI's
  `--check` fails otherwise.
- `node --test "features/**/*.test.ts"` (Node 24 strips types): pure modules import with explicit `.ts` extensions,
  use erasable syntax only (no enums, no parameter properties) and may not import `.tsx`, JSON or `@/` paths. Tests
  read the shared fixtures by repository path: `generator/tests/fixtures/{validation_cases,brand_golden}.json` and
  `web/api/testdata/contract/{generate_headers,events}.json`.
- `features/preview/brand.ts` must change in the same commit as `generator/genkit/brand.py`; `brand.test.ts` fails on
  any drift over the 200 seeded accents and on every style's content roles.
- What the browser stores (for the privacy page): `sessionStorage["android-base.session"]` = `{id, landed}` (random
  UUID v4, gone with the tab); `localStorage["android-base.draft"]` = the configurator answers, no signing passwords,
  no date, no identifier, written only once an answer differs from the catalogue's defaults and removed by Start over
  or when the answers are back at the defaults (`draftToStore`, tested in `state.test.ts`); `localStorage["theme"]`
  only if the visitor picks light or dark; `sessionStorage["android-base.admin-token"]` on `/admin` only.
- What the browser sends to a third party: the style showcase and the Look step load the preview typefaces (the
  suggestions and the one typed) from fonts.googleapis.com and fonts.gstatic.com, which see the visitor's IP address.
  The site's own three families are self-hosted by `next/font`. The FAQ says so; the privacy page must too.
- The draft counts settings by what they say: a blank text field or flavour URL, or a value equal to the field's
  default, is no answer, because the spec builder leaves it out and the generator assumes the default. Typing a
  deep-link scheme and clearing it again therefore leaves no draft.
- The site only ever restores or switches to a selectable target (`available` or `beta`). A draft for a target since
  hidden or put back to coming soon opens on the first selectable one; a target `/api/v1/targets` reports as off
  gives way to the first one the server generates. Telemetry's first `step_viewed` is sent after the draft is read,
  so it names the restored target.
- `returning` is true exactly when a draft existed at load. A visit that changes nothing stores nothing, so it does
  not make the next visit returning; clearing site data or Start over resets it.
- Feature resolution on the site: ticking adds what the feature implies; unticking removes everything that implies it;
  a feature the visitor cannot tick (`implied_only`: Firebase) stays only while something chosen implies it, so it
  leaves with the last such feature (unticking push removes Firebase, keeps Analytics and Flags). A preset whose list
  carries an `implied_only` feature nothing in it implies would lose it on the site; WP01's catalogue check should
  refuse such a preset. A design style's `requires` (Glass needs `liquidglass`) is kept on through presets, platform
  switches and restored drafts; unticking it puts the target's default style back and the hint says so, with Undo.
- `NEXT_PUBLIC_API_BASE` (empty in production: same origin) and `NEXT_PUBLIC_BUILD` (the short commit, sent in
  `X-Client`; `dev` when unset) are read at build time.
- The preview tab rule is A5.3: sample, paging, search, profile, settings, then modules, five at most, a `home`
  module when nothing provides a tab. If WP02-M2's `tabs.py` lands a different order, change `features/preview/tabs.ts`
  and its test in the same change.
- Generator warnings reach a visitor only through `X-Keystores-Skipped`; everything else the generator says about a
  spec (`warnings`, `ignored_fields`, `notes`) is shown to the operator only, in the admin's generation details.
- A generate answer of 503 `unavailable` means a deploy stopped the server mid-run; the site shows the server's
  message and leaves Generate enabled, so the visitor retries with the same answers. Only a 401 on `/admin` signs out.
- The npm audit of the pinned dependencies is not clean (see Open issues); bumping `next` changes `package-lock.json`
  and needs `npm ci` and the acceptance run again.
- **A colour token lives in two places in `app/globals.css`:** its `light-dark(light, dark)` in `@theme`, and its
  light value again in the `@supports not (color: light-dark(#000, #fff))` block, which is all Safari before 17.5
  (iOS 16, iOS 17.0 to 17.4) gets. Change both. Those browsers see the light palette only, and the theme toggle hides
  itself there (`not-supports-[…]:hidden`).
- A `position: sticky` box inside a grid or flex row needs `self-start` (a stretched item is as tall as its container
  and cannot move) and no `overflow: hidden` ancestor below the scroller (`overflow-clip` clips without becoming one).
  The live preview is `lg:sticky lg:top-24 lg:self-start`.
- The drawn phones (`AppPreview`) are pictures: `aria-hidden`, tabs and scroller at `tabindex -1`. Anything a keyboard
  or screen reader user needs to change in a preview goes in a control outside the phone, as the Screen radiogroup
  and the preview theme switch do.
- A request's failure message branches on `ApiError` (the API answered), never on `Error`: `fetch` rejects with a
  `TypeError` when nothing answered, and its message is the browser's ("Failed to fetch").
- The session id is a UUID v4 built from `crypto.getRandomValues`, not `crypto.randomUUID`, which exists only in
  secure contexts (testing over plain http from a phone on the LAN is not one).
- File comments in `web/frontend` are `//` line comments. A `/** */` block at the top of a module attaches to the
  first declaration after it and shows up in that declaration's hover.
- The Review step's next steps are per target (`NextSteps` in `ReviewStep.tsx`): Android names `:app:installDevDebug`,
  multiplatform `:androidApp:installDevDebug` and `cd iosApp && xcodegen generate`, and any other target "follow its
  README". A template that renames its app module or flavours changes that list too.
- Preview copy is the template's: "Samples / Pulled from a live API", the scaffolded module's "Nothing here yet / When
  there is something to show, it appears on this screen.", and the Settings screen row for row as
  `feature/settings/Settings.kt` draws it (Appearance; Haptic feedback; Language; Require unlock; Privacy / Share usage
  data; Account / Sign out; About / Open source licences; Legal / Privacy policy, Terms of service). Rewording or
  reordering those in the template means updating `features/preview/screens.tsx`.
- **Sticky chrome needs scroll padding.** A control under a sticky bar still counts as in view, so focusing it does not
  scroll (WCAG 2.4.11). `html` has `scroll-padding-top: 5rem` for the landing nav (4rem tall); `/admin` sets its own
  from the filter bar's measured height while the bar sticks. A new sticky element needs the same, and an anchor
  target needs no `scroll-margin` of its own.
- **Anything that moves on its own needs a Pause on the page** (WCAG 2.2.2): reduced motion decides only whether it
  starts. The showcase and the Motion step's cards have `PauseButton`; a new looping preview gets one too.
- **A `sr-only` element inside a horizontal scroller needs a positioned ancestor inside that scroller.** It is
  absolutely positioned; with its containing block outside the scroller it is not clipped and widens the page (the
  step bar's buttons are `relative` for this).
- **The nav must fit 320 px.** Below `md` its actions are 36 px icons with hidden names, and below 360 px the Beta
  badge hides; anything added to the nav needs the 320/360/375 `scrollWidth` check again.
- **Outline colours:** a field's or switch's outline is ink-500 (3:1 or more on every surface); ink-600 and lighter are
  for edges nobody has to find. A selected card or chip is the full accent plus a 1 px ring, so selection is not
  colour alone. A selected segment or filter pill is inverted (`bg-ink-100 text-ink-950`), as `Segmented`, the Screen
  radiogroup and the admin's window, status and target switches are: an ink-700 pill on the ink-900 track and a label
  going from ink-400 to ink-100 both measure under 3:1 (WCAG 1.4.11).

- **Lengths are counted in code points**, as Python's `len()` counts them: the app and display names, keystore
  passwords, the package name, the report form's minimums and the generic field limit go through `codePoints` in
  `lib/text.ts`, never `String.length` (UTF-16 units). An emoji is one code point and
  two units, so `.length` lets a three-emoji password past a minimum of 6 that the generator refuses.
- **The ResizeObserver loop message is not a client error.** `reportErrors` drops errors whose message starts with
  "ResizeObserver loop": the browser fires it when an observer's callback changes the size of what it observes (the
  live preview's fit-to-width does), and nothing has failed.
- **Every looping preview takes its paused state from `usePaused`** (`components/primitives.tsx`) and puts a
  `PauseButton` beside it. `usePaused` reads reduced motion through `useSyncExternalStore` with a server snapshot of
  `false`; reading `matchMedia` (or framer-motion's `useReducedMotion`) during the first client render makes the
  markup differ from the prerendered HTML, React throws error #418 and re-renders the whole page on the client, and
  the visit lands in `errors`.
- **Element styles go in `@layer base`, the site's own classes in `@layer components`** (`app/globals.css`). Tailwind
  v4 puts utilities in `@layer utilities`, and any rule outside a layer beats every utility whatever its specificity,
  so an unlayered rule silently disables the utilities that should override it.
- **Focus:** every control shows the 2 px accent outline 2 px outside it on `:focus-visible`, following its own
  corners (no `border-radius` on the ring). Fields (`input` other than checkbox, radio and colour, `select`,
  `textarea`) draw the same ring over their border (`outline-offset: -1px`) on any focus, from the base layer; a
  field needs no focus classes of its own. A styled label over an `sr-only` input shows the ring with
  `has-[:focus-visible]:outline-2 has-[:focus-visible]:outline-accent`.
- **Mint, amber and rose are text colours.** A `Badge` lays a 10% tint of its colour under its text, which costs
  contrast; the light values are set so each reads at 4.5:1 or more as a Badge on ink-950 to ink-800 and as plain text
  on ink-950 to ink-700. Changing one means measuring both again, in the `@theme` block and the `@supports` fallback.
  Text is never drawn at reduced opacity to make it quieter: use a lighter ink step that still passes (ink-400 and up).
  That holds for disabled controls too: a disabled `ChoiceCard` is marked by its dashed ink-600 edge, no fill and the
  not-allowed cursor, never by fading, because its text (the platforms' "Coming soon") is often the only place saying
  why it cannot be picked.
- **A `<summary>` with its own marker needs `list-none [&::-webkit-details-marker]:hidden`;** Safari ignores
  `list-style` there.
- **The theme choice is per browser, not per tab:** the toggle listens for `storage` events on the `theme` key, so a
  choice made in another tab applies at once.
- **A control that disables or removes itself must keep the focus.** A focused element that turns `disabled` or
  unmounts drops the focus to `<body>`, and a keyboard or screen reader user is left nowhere. A button that disables
  itself while its action runs takes `focusableWhenDisabled` (`Button`: `aria-disabled`, presses and form submission
  cancelled); a native control does the same with `aria-disabled` and a guarded handler (the report status select, the
  Derive button). A control that removes itself moves the focus first to something that stays: Start over's Undo
  hands it to Start over, the Features hint's Undo to the checkbox of the feature it changes back, the sent report to
  the confirmation's heading. Do not key a component on data a save changes (the note box takes the stored note into
  its draft during render instead), since remounting it loses the focus inside it.
- **framer never settles an animation that is stopped part-way** (a newer animation on the same value, a pause, an
  unmount, the reset to rest), so a loop awaiting one waits forever. Looping previews run on `loop()`
  (`features/preview/loop.ts`), whose waits end the moment the effect's cleanup stops it, so nothing after them runs
  on an unmounted scope. A part the visitor can press (the motion card's button) is timed, never awaited.
- **Start over keeps one Undo snapshot until the next edit.** A second press before any edit keeps the first
  snapshot (`snapshotForUndo`), because the answers on screen are already the defaults and the draft is gone. Whether
  there is anything to undo is `isUntouched` (`draft.ts`), not the draft alone: the draft never holds signing details,
  so passwords, organisation or country typed with nothing else changed still get an Undo.
- **The draft is written 300 ms after an edit, and at once on `visibilitychange` to hidden or `pagehide`**, so an edit
  made just before the tab closes is kept.
- **The events batch limit (8 KB) is counted in UTF-8 bytes**, as the API reads the body, never with `String.length`.
- **The site offers a platform only when its key is in `OFFERED` (`web/frontend/lib/catalogue.ts`)**, today
  `android` alone (REQUIREMENTS 36, Android first). Every other target in the catalogue reads as coming soon on every
  surface (platform cards, hero badges, FAQ), whatever its catalogue status, and a draft or link for it lands on
  Android. Compose Multiplatform and Swift are named as coming soon from `ANNOUNCED` while the catalogue has no target
  for them; once it has, its title, summary and status note are used. **Phase B ships multiplatform by adding
  `"multiplatform"` to `OFFERED`** (one line, with its README checked against the Review step's next steps); Swift
  stays out until its own release. A target's catalogue status still caps it: offering a `coming_soon` or `hidden`
  target changes nothing. Copy built from the catalogue reads only the selectable targets (`selectableTargets` in
  `features/catalogue/platforms.ts`): the licence answer and the footer never name a coming-soon target's licences.
- **A target the API reports as not enabled reads as coming soon** on the Platform step too. The phase-A deploy should
  also set the API's `ENABLE_TARGETS=android` (its default is `android,multiplatform`), so the API does not generate
  an unverified template for anyone calling it directly.
- **The live preview's view (theme and screen) belongs to the configurator**, not to `LivePreview`, which remounts
  with each step.
- **An empty typeface is the target's default, not a missing font.** The generator reads `font_name: ""` as
  `DEFAULT_FONT` (`_text(...) or DEFAULT_FONT` in `spec.py`) and `validateSpec` does the same, so everything that shows
  the typeface (the previews, the font check, the suggestion chips, Review, a report's attached answers) reads
  `typeface(state.fontName, target)`. Spaces alone are drawn as the default too, but both validators still refuse them
  (the font pattern needs a letter or digit first). Only a non-blank name can be "not found".
- **The build name comes from Vercel's commit.** `BUILD` is `NEXT_PUBLIC_BUILD`, else the first 7 characters of
  `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` (Vercel's framework variable, exposed while "Automatically expose System
  Environment Variables" is on, the default), else `dev`. It names `X-Client`, a client error's `release` and a
  report's `appVersion`, so a build made outside Vercel should set `NEXT_PUBLIC_BUILD`.
- **What a report and a page error keep** (for the privacy page, WP12): a report always keeps its kind, severity,
  area, summary, details and steps, the email if given, `appVersion` (the site's build), a coarse
  "browser · OS · device class" string the API derives (never the raw user agent) and the daily-rotating visitor hash.
  Only when "Attach what you configured" is left ticked, and only once the configurator has loaded (the checkbox shows
  only then), does it also keep the configurator answers (platform, app and package name, features, preset, min SDK,
  motion style, typeface, accent) and the page URL (origin and path, never the query or fragment): `Feedback.tsx`
  sends `pageUrl` with the answers or not at all, and the API stores it only from the body. A page error
  (`/api/v1/client-error`) keeps its message, stack, page path and release. The FAQ's storage answer and the
  checkbox's hint ("And this page's address.") say the same since run 13.
- **One alert for the admin's failed loads.** A panel never raises its own `role="alert"`: it reports its error
  through `PanelFailures`, and the dashboard's single alert reads "Not every panel loaded." with each distinct message.
  The sentence carries no count, because the panels fail one by one and a changing count is announced each time.
- **A control inside a choice card's `<label>` must cancel its click** (`event.preventDefault()`), or using it also
  selects the card: the motion cards' drawn "Press me" button does.
- **A field is flagged once its value is complete or the field is left**, not while it is typed: the brand colours'
  hex fields wait for six characters or a blur. Buttons that need an answer first stay enabled and say what is
  missing when pressed (report Send, admin Sign in).
