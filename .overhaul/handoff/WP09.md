## Public API (what the frontend and scripts call)

Every JSON response carries `Content-Length`. Every error body is
`{"error": "<sentence for people>", "code": "<machine code>", "field": "<spec field, when there is one>"}`.
Codes: `invalid_json`, `invalid_spec`, `too_large`, `unreadable`, `unsupported_media_type`, `unknown_target`,
`target_unavailable`, `rate_limited`, `generator_failed`, `timeout`, `invalid_events`, `invalid_feedback`,
`invalid_report`, `unauthorized`, `bad_request`, `not_found`, `unavailable`, `internal`.
Every `POST` must be `Content-Type: application/json` (charset allowed), otherwise **415**.

### `GET /api/v1/targets`

```json
[{"key": "android", "title": "Android Native", "status": "available", "summary": "…", "enabled": true},
 {"key": "multiplatform", "title": "Compose Multiplatform", "status": "beta",
  "status_note": "Beta: the iOS app is not yet verified on a Mac", "summary": "…", "enabled": true},
 {"key": "ios", "title": "Swift", "status": "coming_soon", "summary": "…", "enabled": false}]
```

Catalogue order; `status = "hidden"` targets are omitted. `enabled` (an addition to A10.1's shape) says whether this
deployment generates the target (`ENABLE_TARGETS` ∩ catalogue).

### `GET /api/v1/catalogue` (legacy alias `GET /api/options`)

The catalogue v2 document exactly as the generator printed it, `ETag` (strong, sha256), `Cache-Control: no-cache`;
`If-None-Match` honours lists, `W/` and `*` → 304 with no body.

### `GET /api/v1/health` (legacy alias `GET /api/health`)

```json
{"ok": true, "uptime_s": 20, "database": "ready|connecting|off", "targets": ["android", "multiplatform"],
 "generator_commit": "…", "telemetry": {"queued": 0, "written": 13, "dropped": 0, "failed": 0}}
```
(`telemetry` only when `DATABASE_URL` is set.) Not rate limited and not recorded in `requests`: probes and uptime
monitors poll it from one address every few seconds.

### `POST /api/v1/{target}/generate` (legacy alias `POST /api/generate` = android)

Request: the spec JSON (v2 per A1.3, or v1 which Python upgrades), at most `rules.spec_bytes_max` (32 KB) → else 413.
Session headers (optional): see the next section. The precheck refuses with 400 `invalid_spec` + `field`:
invalid UTF-8, not JSON, not an object, trailing data, depth > 6, any object with > 64 members, `features` > 64,
`feature_modules` > `rules.feature_modules_max` (12), `languages` > `rules.languages_max` (10), `keystores` (top level
or under `android`) > `rules.keystores_max` (4), any other array > 64, identifier fields and object keys > 120 bytes,
other strings > 256 bytes, any control character in any string, `platform` present and not equal to the route's
target. `field` is the dotted path (`android.keystores`, `feature_modules`). Keys are walked in sorted order, depth
first, so a spec with several faults is always refused for the same field.

Responses:
- 200 `application/zip`, `Content-Disposition: attachment; filename="<Project>.zip"`, `Content-Length`,
  `X-Project-Name`, `X-Generation-Ms` (generator's `elapsed_ms`), `X-Keystores-Skipped` (comma list, only when
  the result carries `keystores_skipped`).
- 400 `invalid_spec` with the generator's message and `field` (headless `kind: "invalid"`).
- 500 `generator_failed` (headless `kind: "internal"`, a crash, non-JSON stdout, or ok without a zip) or `timeout`;
  generic message, traceback/stderr only in the error list. The error list row keeps the generic message
  (`android: The generator failed.`) but is grouped by a fingerprint of the failure's signature: the final exception
  line (digits and paths masked) plus the innermost frame in the generator's own code as `module.function` (line
  numbers and install path left out), or for a child that never answered, its exit status and last stderr line. So
  distinct bugs are distinct rows, and the same bug after an edit elsewhere in the file, or on another deployment,
  stays one row.
- 404 `target_unavailable` (in the catalogue, not enabled, e.g. `ios`) or `unknown_target`.
- 503 `unavailable` when the server shut down while generating (recorded as `abandoned_running`); retrying reaches
  another instance.
- 429 `rate_limited` with `Retry-After: 3600` (`RATE_LIMIT_PER_HOUR`, default 30, per IPv4 address or IPv6 /64).

### Session headers (generate route only)

| Header | Rule | Stored |
|---|---|---|
| `X-Session-Id` | UUID v4, whole value, case-insensitive | lowercase in `generations.session_id` and server events; otherwise ignored (null) |
| `X-Config-Ms` | digits only, 0 … 7 200 000 | `generations.config_ms` and server events; otherwise ignored |
| `X-Client` | 1–64 printable ASCII | class only: `web` when it starts with `android-base-web/` + ≥ 1 char; else `bot` when the UA is a crawler/headless browser; else `cli` |

A malformed header is ignored, never an error. The child process only receives the spec on stdin, so the headers
never reach Python. The full case list is `web/api/testdata/contract/generate_headers.json` (25 cases: `cases[]` of
`{name, headers, expected: {session_id, config_ms, client}}`); WP10's `request.ts` tests read the same file.

### `POST /api/v1/events`

```json
{"session_id": "<uuid v4>", "events": [
  {"name": "landed", "referrer": "https://news.ycombinator.com/item?id=1", "utm_source": "hn",
   "utm_medium": "social", "utm_campaign": "launch", "returning": false, "viewport": "lg"},
  {"name": "step_viewed", "target": "android", "step": "platform"},
  {"name": "platform_selected", "target": "android"},
  {"name": "step_viewed", "target": "android", "step": "identity"},
  {"name": "preset_chosen", "target": "android", "preset": "standard"},
  {"name": "generate_clicked", "target": "android"},
  {"name": "download_started", "target": "android"}]}
```

- 1–20 events per batch, body ≤ 8 KB, unknown fields refused (strict decode), the whole batch is refused on any error
  (400 `invalid_events`), 204 otherwise. Rate limit 1 200 per hour per client key.
- Client event names: `landed`, `platform_selected`, `step_viewed` (with `step` ∈ `platform`, `identity`,
  `features`, `look`, `motion`, `build`, `review`), `preset_chosen` (with `preset` = a preset key of that target in
  the catalogue), `generate_clicked`, `download_started`. Server-only names (`generated`, `downloaded`,
  `download_interrupted`) are refused here.
- Every event except `landed` needs `target` (a catalogue target key). `landed` takes no target, step or preset; only
  `landed` may carry `referrer` (any URL; the server keeps `scheme://host[:port]`, drops it when it is the site's own
  host: `X-Forwarded-Host` under `TRUSTED_PROXY=vercel`, else the request's `Host`), `utm_source`/`utm_medium`/`utm_campaign` (trimmed, clipped to 64 bytes, no control characters),
  `returning` (bool, default false), `viewport` ∈ `xs` (< 480 px), `sm` (< 768), `md` (< 1024), `lg` (< 1440),
  `xl` (≥ 1440). One `landed` per batch; a second `landed` for the same session is ignored by the database.
- The server adds to the session's visit: country/region/city from Vercel's headers (only under
  `TRUSTED_PROXY=vercel`), browser family, OS family, device class (`Sec-CH-UA-Mobile` first), client class, and a
  visitor hash (salted, daily-rotated, IPv4 or IPv6 /64).
- Send `X-Client: android-base-web/<build>` on events too; without it a browser's events are classed `cli`
  (or `bot`).
- Cases: `web/api/testdata/contract/events.json` (`accepted[]` with the stored rows, `refused[]`).

### `POST /api/v1/client-error`

`{"message": "required", "stack": "…", "url": "https://site/page?x#y", "release": "<build>"}` (strict, ≤ 16 KB)
→ 204. Stored in `errors` with `kind = "client"`, `path` = the URL's escaped path only (only for an `http(s)` URL with
a host or an absolute path; anything else, e.g. `javascript:…`, stores no path), `detail` = `release <build>\n<stack>`,
fingerprint from the message and the first stack frame. Rate limit 60/hour.

### Admin (`Authorization: Bearer <ADMIN_TOKEN>`; registered only when `DATABASE_URL` is set)

Only a missing or wrong token is **401**. Bad parameters are 400 `bad_request` with `field`; the database not reachable
yet is **503** `unavailable` (keep the last data, show a banner); other failures 500 `internal`.

Common query parameters on every `GET /api/v1/admin/*`:
`from`, `to` (inclusive UTC dates `YYYY-MM-DD`; default: the last 30 days including today; at most 400 days),
`target`, `preset`, `outcome` (one of the 8 outcomes), `country` (two letters, any case), `device_class`
(`mobile|tablet|desktop|unknown`), `source` (the visit source: the lowercased `utm_source`, else the referrer host
without `www.`, else `direct`). Every response starts with `"from"`, `"to"` (inclusive). Which filters apply:
generation-based queries honour all of them (`source` through the generation's session); visit-based ones honour
`target` (sessions with an event for it), `country`, `device_class`, `source`; `funnel` ignores `preset`/`outcome`;
`failures` ignores `outcome`.

  "abandoned_queue", "abandoned_running", "rate_limited"}, "median_ms", "p95_ms" (duration of generated projects),
  "visitors" (daily unique visitors summed over the window), "sessions", "returning_share", "open_errors",
  "new_feedback"}`.
- `funnel` → `{"landed", "targets": [{"target", "steps": [{"key", "sessions"}], "also": {"preset_chosen": n,

- `series` → `{"days": [{"day", "outcomes": {…8…}, "visitors", "sessions"}]}`, one entry per day of the window, zeros

- `adoption` → `{"targets": [{"target", "total", "features": [{"key", "title", "n", "picked", "share"}],

  "failed"}, "off": {…}}], "pairs": [{"a", "b", "n", "failed"}] (n ≥ 5, failed > 0, top 20 by rate), "by_min_sdk",

## Telemetry storage (migrations)

`schema_migrations(version text PRIMARY KEY, applied_at)`; each file runs in its own transaction while the connection
holds `pg_advisory_lock(72710001)`. On a database the old runner migrated, 0001 and 0002 are idempotent and get
recorded on the first boot (verified in `TestIntegrationUpgradesADatabaseTheOldRunnerMigrated`).

- **0003_telemetry_v2.sql**: `generations` gains `target` (default `android`), `outcome` (NOT NULL; old rows
  backfilled from `succeeded` and the old API messages), `session_id uuid`, `config_ms`, `client`, `device_class`,
  `cold_start`, `queue_ms`, `python_ms`, `stream_ms`, `generator_commit`, `failure_field`, `added text[]`,
  `removed text[]`, `architecture`, `design_style`, `languages text[]`, `glass`, `spec jsonb`, and `notes`,
  `ignored_fields`, `warnings` (`text[]`, what the generator said about the spec; each entry clipped); `app_name` and
  `package_name` become nullable; indexes `(target, created_at DESC)` and `(session_id)`. `preset` now holds the
  preset nearest to the resolved features (for a run without a result from the generator, the request's features
  resolved through the catalogue's `implies`). `visits` drops its `(day, visitor_hash, step)` key for an `id`, and gains
  `session_id` (unique when not null), `returning_visitor` (`returning` is a reserved word), `referrer_origin`,
  `utm_source`, `utm_medium`, `utm_campaign`, `viewport`, `country`, `region`, `city`, `browser`, `os`,
  `device_class`, `client`, and a generated `source`. New `events(id, at, session_id, target, name, step, value,
  client, config_ms)`. `feedback.target`.
- **0004_rollups.sql**: `daily_rollup(day, target, preset, outcome, country, device_class, n, p50_ms, p95_ms)` keyed
  on the first six (empty string for unknown), backfilled; each recorded generation re-computes its day's row in the
  same batch (exact percentiles over `duration_ms`).

Retention (hourly, every instance, idempotent): `requests` older than `RETENTION_REQUESTS_DAYS` (30), `events` and
`visits` older than `RETENTION_EVENTS_DAYS` (400); generations older than `RETENTION_NAMES_DAYS` (90) lose
`app_name`, `package_name`, everything in `spec` that identifies the project (`app_name`, `display_name`,
`package_name`, and `api_base_urls`, `web_socket_urls`, `deeplink_scheme`, `deeplink_host` both under `android` and
flat as schema 1 sent them, `ios.bundle_id`, `ios.team_id`; nested keys only when `android`/`ios` are objects), their
`warnings` (they can quote a keystore name or keytool's output), and the `failure_reason` of `invalid` rows (the
message often quotes the rejected input). Not pruned: generator tracebacks in `errors.detail`, which can contain a
project name in a path or a message.

## What the frontend must send (WP10)

- Every `POST` with `Content-Type: application/json` (a `sendBeacon` must use a JSON `Blob`).
- A `session_id` UUID v4 per tab (`crypto.randomUUID()`, `sessionStorage`), in every events body and as `X-Session-Id`
  on generate.
- `X-Client: android-base-web/<build>` on generate **and** on events.
- `X-Config-Ms` on generate: ms from `step_viewed:identity` to `generate_clicked`, capped at 7 200 000 by the client
  (a larger value is dropped, not capped, by the server).
- `landed` once per session with `referrer` (`document.referrer`), the three UTM parameters from `location.search`,
  `returning` (a saved draft existed at load), `viewport` bucket.
- `platform_selected` when the platform step is completed, including when the default is kept, because each target's
  funnel starts there; every later event carries the selected `target`.
- Error bodies: read `error` for the message, `field` to place it, `code` to branch; only a 401 on admin logs out.
  A 503 `unavailable` from generate means a deploy stopped the server mid-run: offer to try again (the spec was
  fine).

## Deviations from MASTER-PLAN, with evidence

1. **Telemetry wait after the response.** A10.1/M1 say telemetry is written asynchronously, never on the response
   path. It is: batches go through a bounded channel to one writer. But commit `11377ec` records that on Vercel a
   goroutine started after the response "is never scheduled and the row is lost" (generations stopped being recorded).
   So `observe` flushes the complete response (every JSON body carries `Content-Length`; the zip already did) and then
   keeps the handler alive until its batch is written, at most 2 s. The client never waits; the process does.
2. **`/api/options` serves catalogue v2.** The v1 catalogue module is deleted by WP01, so the alias returns the same
   document as `/api/v1/catalogue`. A tab of the previous site that refetches it would get the new shape; the old
   generate and track aliases keep working.
3. **`enabled` on `/api/v1/targets`** (added): the site needs to know whether a target can be generated here, apart
   from its catalogue status.
4. **Preset.** Spec v2 has no preset field, so the recorded `preset` is the catalogue preset whose features differ
   least from the resolved set (ties: the default preset, then catalogue order), and `added`/`removed` are relative to
   it. A run the generator did not finish is described from the catalogue (its `implies` closure, which the
   integration test checks against the generator, and its `generator_commit`), so failures are attributed like
   successes.
5. **Server events need a session.** `generated`/`downloaded`/`download_interrupted` are written only when the request
   carried a valid `X-Session-Id`; they exist for the funnel, which counts sessions. `generations` records every
   request regardless.
6. **Feedback** keeps its camelCase body ("as today") and stores a classified agent instead of the raw user agent
   (A10.2: no raw UA anywhere).
7. **Retention** also strips the names from the stored spec and clears `failure_reason` on old `invalid` rows (see
   above). R14.
8. **Geo on generations.** `generations.country` (an existing, never-written column) and a new `device_class` are
   filled from the generate request itself, so the country and device filters work for scripted generations that
   have no session; region and city live only on `visits`.
9. **Timeouts** answer 500 with code `timeout` (not 504) and go to the error list as generator bugs. A run killed by
   shutdown is `abandoned_running`, not a generator bug: no error-list row, 503 to a visitor still connected.
10. **`/api/health`** is kept as a legacy alias as well (monitors may call it).
11. **Load shedding (audit L6)** is not added: the queue is bounded only by the request context. Not in WP09's steps.

## Contract with the generator (verified against the merged WP01 at `709612d`)

The real catalogue and headless result match what Go reads, with two differences: the catalogue also publishes
`rules.features_max` (64), which the precheck now uses instead of its own constant, and the headless result has no
`keystores_skipped` (see "Open issues"). `status_note` is `""` for android, which `/api/v1/targets` omits.


- Catalogue: `version == 2`, `generator_commit`, `targets[].{key, title, status, status_note, summary,
  features[].{key, title, implies, implied_only}, presets[].{key, features}, defaults.{preset, architecture, design_style,
  motion_style}}`, `rules.{spec_bytes_max, features_max, feature_modules_max, languages_max, keystores_max}`. Anything else is
  served untouched.
- Headless: one JSON object on stdout; `ok`, `kind` (`invalid`/`internal`), `error`, `field`, `detail`,
  `project_name`, `elapsed_ms`, `resolved_features`, `notes`, `warnings`, `ignored_fields`, `generator_commit`, and
  optionally `keystores_skipped` (list of keystore names; becomes `X-Keystores-Skipped`; the merged generator does
  not send it). Go reads `kind`, not the
  exit code. The zip path is the last argument; Go checks its size on disk.
- `generate_headless.py` is run with cwd = `GENERATOR_DIR` and `TMPDIR` pointing into the per-request directory, so
  staging must use `tempfile` (A1.8 says it does).
- The integration test generates `{"schema": 2, "platform": t, "app_name": "Integration", "package_name":
  "com.example.integration", "features": <smallest preset, requestable>}`, expects `field == "package_name"` for
  `"Not A Package"`, at least one note for a v1 spec (`network`, `settings`, `min_sdk: 26` flat), and that asking
  for every feature that implies another resolves to the same set in Go (`TargetEntry.Resolve`, the catalogue's
  `implies`) as in the generator (`resolved_features`).

## Rules and gotchas the docs must state

- The privacy page (`docs/telemetry-and-privacy.md`, WP12): stored per generation: target, outcome, timings, the
  sanitised spec (keystore entries reduced to their names), resolved features, nearest preset and differences,
  architecture, styles, languages, SDKs, glass, generator commit, client class, country and device class, session id
  (random per tab), configurator time, the generator's notes, ignored fields and warnings; for 90 days only: app and
  package names and the spec's other identifying fields (server addresses, deep link, Apple team) and the warnings.
  The error list keeps generator tracebacks with no time limit; they can name a project in a path. Per session: a daily-rotated salted hash of
  the network (IPv4 or IPv6 /64), returning flag, referrer origin, UTM, viewport bucket, country/region/city, browser
  family, OS family, device class. No IP address, no raw user agent, no persistent identifier. Cities shown only with
  ≥ 5 sessions.
- `web/README.md` still describes `web/deploy/` (install script, Caddyfile), the old `/api/*` routes and
  "written to a temporary directory that is deleted as the download finishes" (now true). WP12 owns it.
- Running the image anywhere but Vercel: set `TRUSTED_PROXY` (`none` when exposed directly, `hops=N` behind N
  appending proxies). `vercel` behind any other proxy trusts a forgeable header.
- `.vercelignore` follows `.gitignore` syntax: root-only paths need a leading slash (`/tools/`, `/.claude/`), or
  `templates/android/tools/perf/` and the templates' vendored `.claude/skills/` would be dropped from the upload the
  API image is built from, and every project generated on the site would lack them.
- The image has no git, so the generator reports `generator_commit: "unknown"` unless `generator/COMMIT` exists at
  build time (`record.generator_commit()` reads it; `.gitignore` lists it, `.dockerignore` admits it). CI (WP13)
  writes `git rev-parse --short=12 HEAD` into `generator/COMMIT` before `docker build`, or the admin's
  `failures.by_commit` and every generated project's `generator-spec.json` say `unknown`.
- A target missing from the catalogue is only a warning at boot and in `-selftest`
  (`"ENABLE_TARGETS names a target the catalogue does not list"`); a container check must grep the selftest log for
  each target it expects (`"msg":"selftest","target":"android"`).
- `/api/v1/{target}/generate` answers 404 `unknown_target` for a key the catalogue lacks (today `ios` and
  `multiplatform`) and `target_unavailable` for one it lists but this deployment does not enable.
- CI (WP13): Go version from `web/api/go.mod`; `staticcheck`; the store tests need a Postgres service and
  `TEST_DATABASE_URL`; the container smoke is `docker run … /app/server -selftest`.
- Deploying this release (WP12/WP13): migration 0003 makes `generations.outcome` NOT NULL and drops the `visits`
  primary key. During a rolling deploy, an instance still on the old code fails its `generations` inserts once 0003
  has run, and its `/api/track` visit inserts no longer deduplicate. It lasts until the old instances are gone; deploy
  in one step (Vercel does) or accept the gap.
- Health endpoints are neither rate limited nor recorded, so a probe may poll them as often as it likes.
- A script calling `POST /api/v1/{target}/generate` should retry a 503 `unavailable`: a deploy stopped the server
  while it generated, and the spec was fine.
- The error list (`errors`) groups generator failures by their bug, not their message; resolving a row hides only
  that bug, and a resolved bug that happens again reopens its row.

## Open issues

- **Skipped keystores are no longer reported to the visitor (generator, WP01 follow-up).** The v1 headless result had
  `keystoresSkipped`; A1.8's v2 result dropped it, so the merged generator only puts the reason in `warnings`. The API
  still reads an optional `keystores_skipped` and turns it into `X-Keystores-Skipped`, which the site's
  `web/frontend/lib/api.ts` reads, but against the real generator the header is never sent: a visitor whose keystores
  keytool refused gets a project whose variants fall back to debug signing without being told. The fix is one field in
  `generator/genkit/core/headless.py` (`"keystores_skipped": [...]`, the `skipped` list `targets/android/keystores.py`
  already computes, carried out through `pipeline.build`). Not done here because `generator/**` is WP01's; nothing in
  the API changes when it lands. The image ships the JRE, so in production this needs keytool to fail, not be absent.
- Multiplatform integration and selftest coverage arrive with WP07: the catalogue has no `multiplatform` target yet,
  so the integration test skips it by name and the selftest warns. No API change is expected.
- The daily rollup can undercount by a row under concurrent writes from two instances to the same key; the next
  write to that key recomputes it. Single-instance writes are serialised by the writer.
- Vercel freezing behaviour after a flushed response is inferred from `11377ec`, not measured; `telemetry.dropped` and
  `failed` in `/api/v1/admin/health` will show if batches are lost.
- The 2 s telemetry wait is skipped while the database has never connected, but not when it becomes unreachable later:
  then each write takes up to its 5 s timeout, the queue backs up, and every request lingers the full 2 s after its
  response until the 1 024-slot queue is full and batches are dropped. A health signal in the writer (skip the wait
  after a failed write until one succeeds) would fix it; not done, because it changes the Sink interface for an
  outage case the admin's `telemetry.failed` already reveals.
- `-selftest` passes when an `ENABLE_TARGETS` entry is missing from the catalogue (a warning), so a container check
  greps the log per expected target (see the rules above); a strict flag can come with WP07, once every default
  target is in the catalogue.
- The failing-pairs query (`failures.pairs`) unnests every row's features against themselves. Measured on Postgres 17
  in Docker on the dev machine: 20 000 generations with 24 features each on average take 2.8 s; a variant that
  first collects the pairs of failed rows and then counts them with `@>` took 8.4 s, so it was not adopted. At the
  site's traffic the 400-day window stays well under that; if it grows, cap the pairs window or precompute pair
  counts in the rollup.
- A failed run's features drop keys the catalogue does not list: an older spec's renamed feature keys are upgraded
  only by the generator, so such a failure is counted without them.
