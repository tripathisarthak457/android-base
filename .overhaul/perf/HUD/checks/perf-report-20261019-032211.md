### Where the points went

- **Janky frames** −25.0 of 25. Open Janky frames by screen and start with the worst screen. The usual causes: recomposition on every frame of an animation (read animated values in graphicsLayer, offset or drawBehind lambdas), alpha on a full-screen layer, work on the main thread during a transition, and a first frame that builds a whole screen. Record a trace with the android-profiler skill to see which. See `docs/PERFORMANCE-OVERLAY.md#janky-frames`
- **Frame time p90** −10.0 of 10. Ordinary frames take most of their budget. Look for layouts measured twice (intrinsics, nested weights), lists without contentType, and work in composition that belongs in remember or the draw phase. See `docs/PERFORMANCE-OVERLAY.md#frame-time-percentiles`
- **Frame time p99** −10.0 of 10. The slowest frames run past their budget. These are usually first frames: a screen built for the first time, a shader compiled on first use, or a list item type seen for the first time. Pre-warm with the baseline profile, and keep first frames small. See `docs/PERFORMANCE-OVERLAY.md#frame-time-percentiles`
- **Cold start** −10.0 of 10. Start-up does too much before the first frame. Keep Application.onCreate and the first screen's creation free of I/O and of eager singletons, make sure the baseline profile is compiled, and measure with tools/perf/perf.sh coldstart on devRelease. See `docs/PERFORMANCE-OVERLAY.md#start-up`
- **App memory (PSS less graphics)** −10.0 of 10. The app keeps more memory than the 48 MB budget. Look for caches without a bound, images decoded at full size, and screens that hold their data after they close. A heap dump from the profiler shows who owns it. See `docs/PERFORMANCE-OVERLAY.md#memory`
- **Slow frames** −5.0 of 5. Frames over 16 ms miss even a 60 Hz budget. Find them in Frame times and record a trace of that moment. See `docs/PERFORMANCE-OVERLAY.md#slow-and-frozen-frames`
- **R8** −5.0 of 5. This build is not shrunk by R8, which also optimises the code. Release builds are; measure one: devRelease. See `docs/PERFORMANCE-OVERLAY.md#build-checks`
- **Baseline profile** −5.0 of 5. ART has not compiled this build with the baseline profile, so its first use of each screen runs interpreted. On a debuggable build it never will; install devRelease. Otherwise run tools/perf/perf.sh, or adb shell cmd package compile -f -m speed-profile, and turn on the baselineprofile feature if the project lacks one. See `docs/PERFORMANCE-OVERLAY.md#build-checks`
- **Not debuggable** −5.0 of 5. A debuggable build turns off most of ART's compilation, so it is several times slower than the release. Its numbers are pessimistic; measure devRelease. See `docs/PERFORMANCE-OVERLAY.md#build-checks`
- **Long main-thread work** −3.8 of 5. The main thread did more than 50 ms of work for single frames. StrictMode below names disk and network calls; a trace names the rest. Defer what is not needed for the first frame. See `docs/PERFORMANCE-OVERLAY.md#long-main-thread-work`
