# WP14 Generator project tools

Wave 3, after WP02-M2 (the v2 scaffolder, `modes.py`, the modular layout) and WP06 (the `database-entities` region)
have merged. Python 3.12, standard library only; Gradle only to prove generated and modified projects build (light).
Lock budget: Gradle about 1 h.

## Why

Requirement 10 asks for practically useful generator features. The most valuable one for PeriFlow- and VitFleet-style
users is missing: bringing template improvements into a project that was generated earlier and has been edited since.
The existing `add_feature.py`/`remove_feature.py` run on existing projects, so after the overhaul they would scaffold
v2-shaped code (`:core:mvi`, `api/` packages, `AppError`) into v1 apps that cannot compile it, and `remove_feature.py`
knows nothing about modular `:api`/`:impl` pairs (MASTER-PLAN A1.10).

## Steps

1. **`genkit/tools/project.py`**: load a project's `generator-spec.json`; a record without `schema: 2` (or no record)
   is a v1 project: every tool refuses it with one clear message that names `docs/upgrading-v1-apps.md`. Read the
   architecture, features, feature modules, tabs and languages from the record; verify the tree matches enough to
   proceed (settings includes for the recorded modules). Require a clean git work tree for every writing tool
   (`--allow-dirty` overrides, with a warning).
2. **`add_feature.py` / `remove_feature.py`**: both modes. In modular projects a name means four modules
   (`:data:<n>:api|impl`, `:feature:<n>:api|impl`); registrations (settings includes, `:app` dependencies, shell tab,
   `database-entities` entries when `database` is on) are added or removed through the same anchors the generator
   uses; `remove_feature.py` refuses when another module still imports the feature's `api` package (it lists the
   importers) and removes the module's shared keys from `core/navigation` in compact mode. Both update
   `feature_modules` in the recorded spec.
3. **`make_modular.py <project>`**: runs `modes.py` on a compact project (the same transform generation uses),
   updates `architecture` in the record, refuses a project that is already modular. Every moved source file must be
   byte-identical (checked before writing the record).
4. **`add_tab.py <project> <module>`**: links an existing feature module as a tab in `tabs.py`'s order rules
   (5-tab cap with a clear refusal, icon rotation), updates the record.
5. **`add_language.py <project> <tag>`**: strings for every module from `generator/translations/android/<tag>/`,
   `localeFilters`, the locale config, the record. Refuses a tag the generator has no translations for.
6. **`upgrade_project.py <project> [--diff]`**: read `generator_commit` from the record; if that commit is not in the
   generator's git history, refuse with the commit id. Regenerate the recorded spec at that commit (a temporary
   `git worktree` of the generator repository) into `base/`, and at the current commit into `theirs/`, both in a
   temporary directory. For each path: unchanged in theirs → skip; new in theirs → add unless the project already has
   a different file there (report it); deleted in theirs → delete only if the project's copy equals base; changed in
   theirs → `git merge-file` the project's copy with base and theirs, leaving conflict markers on conflict; binary
   files → take theirs only if the project's copy equals base. Files the project added (no base) are never touched.
   Print a summary (added, updated, merged cleanly, conflicts, skipped) and write it to `upgrade-report.md` in the
   project; `--diff` prints the patch and writes nothing. The record's `generator_commit` is updated only when there
   are no conflicts.
7. **Tests** (`test_project_tools.py`): add and remove in a compact and in a modular project (file-level assertions);
   refusal on `fixtures/v1/periflow.json`-shaped projects; `make_modular` byte-identical moves; `add_tab` cap;
   `add_language`; `upgrade_project` on a fixture pair with a local edit that merges cleanly, a local edit that
   conflicts, a file deleted upstream, and a user-added file left alone.

## Acceptance

`$O/accept.sh` (`set -euo pipefail`, in the background, ends with `ACCEPT OK`):

```bash
#!/usr/bin/env bash
set -euo pipefail
export ANDROID_HOME=C:/Users/crazyhusir/AppData/Local/Android/Sdk
OV=D:/projects/tools/.overhaul; W=$OV/wt/WP14; L=$OV/bin/locked; O=$OV/out/WP14
G="git -c user.name=wp14 -c user.email=wp14@localhost"
cd $W/generator
python3 -m unittest tests.test_project_tools -v
python3 -m unittest discover -s tests -t .
for mode in standard standard-modular; do
  rm -rf $O/$mode && python3 create_project.py --spec tests/fixtures/v2/$mode.json --out $O/$mode --no-zip --force
  (cd $O/$mode && git init -q && git add -A && $G commit -qm generated)
  python3 add_feature.py orders --tab --project $O/$mode
  (cd $O/$mode && $L gradle ./gradlew assembleDevDebug testDevDebugUnitTest --console=plain)
  (cd $O/$mode && git add -A && $G commit -qm orders)
  python3 remove_feature.py orders --project $O/$mode
  (cd $O/$mode && $L gradle ./gradlew assembleDevDebug --console=plain)
done
# v1 refusal names the upgrade guide
mkdir -p $O/v1 && cp tests/fixtures/v1/periflow.json $O/v1/generator-spec.json
set +e; python3 add_feature.py orders --project $O/v1 > $O/logs/v1.log 2>&1; rc=$?; set -e
test $rc -ne 0
grep -q 'upgrading-v1-apps.md' $O/logs/v1.log
# upgrade from the WP02-M2 merge commit to HEAD on a project with a local edit
M2=$(git -C $W rev-parse merged/WP02-M2)                        # the orchestrator tags every merge (MASTER-PLAN B.5)
python3 $O/generate_at.py $M2 tests/fixtures/v2/standard.json $O/up                 # yours: generates at a commit via a temp worktree
(cd $O/up && git init -q && git add -A && $G commit -qm old && printf '\n' >> README.md && $G commit -qam local)
python3 upgrade_project.py $O/up --diff > $O/logs/up-diff.log
python3 upgrade_project.py $O/up
(cd $O/up && $L gradle ./gradlew assembleDevDebug testDevDebugUnitTest --console=plain)
echo ACCEPT OK
```
