## 2. Technique inventory (what Telegram does, evidence, parameters)

Cross-checks are in Telegram 13.0.2. Where the book (source 1) differs from 13.0.2 I say so.

T1. Pull-based, time-based animated value read inside draw (AnimatedFloat)
- [SRC] ui/Components/AnimatedFloat.java, 231 lines (book says 219 for 11.4.2). The value object has no animator and no listener. The owner calls set(target) from onDraw/dispatchDraw (comment at :124-125) and the object returns the current value.
- [SRC] :154 retarget threshold 0.0001; :156-158 on retarget startValue = current value, transitionStart = SystemClock.elapsedRealtime(); :166-167 progress = (now - start - delay) / duration clamped 0..1 (time, not frame count); :170-173 linear lerp unless an interpolator is given; :177-182 while t < 1 it calls parent.invalidate() and/or an invalidate runnable; :119-122 get() is @Deprecated with a comment saying not to use it.
- [SRC] No velocity carry-over: only the value is kept on retarget (compare Compose, section 4 M1).
- [SRC] Scale of use: AnimatedFloat appears in 171 files, 411 constructor calls; CubicBezierInterpolator in 498 files; ValueAnimator in 288 files; SpringAnimation in 40 files.
- [CLAIM] source 1 ch.2 lab: 500 rows, 250 ms highlight, one ValueAnimator per row vs one AnimatedFloat per row; no results published in the book.

T2. One custom View paints each chat message; layout precomputed in the model
- [SRC] ui/Cells/ChatMessageCell.java is 29,584 lines (book: 24,903 in 11.4.2); :263 extends BaseCell; the only addView( hit in the file (:10834) is a callback registration on an emoji drawable, not a child view. So still no child views. ImageReceiver (messenger/ImageReceiver.java:57) is a plain class, not a View.
- [CLAIM] source 1 ch.3: onMeasure returns a stored height, text StaticLayouts are built in MessageObject.generateLayout when the message arrives, hit-testing is hand-written. [CLAIM] source 12 says the same in one sentence.

T5. Frame pacing and refresh rate
- [SRC] messenger/AndroidUtilities.java:290 screenRefreshRate defaults to 60; :2768-2778 it is set from Display.getRefreshRate(), and screenMaxRefreshRate from the display's supported rates (book says the 60 default is never re-read; in 13.0.2 it is, in checkDisplaySize).
- [SRC] AndroidUtilities.java:2817-2840 setPreferredMaxRefreshRate writes WindowManager.LayoutParams.preferredRefreshRate = screenMaxRefreshRate; used for overlay windows: AvatarPreviewer.java:152, BubbleActivity.java:331, PipRoundVideoView.java:293, PipVideoOverlay.java:963 and :1155, CustomEmojiReactionsWindow.java:300, ReactionsEffectOverlay.java:789. A RefreshRateController class exists (messenger/utils/RefreshRateController.java) but its use in LaunchActivity is commented out (LaunchActivity.java:395 and :855).
- [SRC] ImageReceiver.java:226 DEFAULT_CROSSFADE_DURATION = 150 ms. :1842-1852 fade alpha stepping: background-thread draw path advances alpha by elapsed ms / duration (first step assumed 16 ms; step clamped to 30 ms when refresh rate > 60); main-thread path advances by a fixed 16 ms-equivalent per draw call. So the main-thread fade is frame-count-based. [CALC] At a step of 16 ms-equivalent per draw and a 150 ms duration it needs about 10 draws: about 167 ms at 60 Hz and about 83 ms at 120 Hz if a draw happens every frame. The summariser's rendering of book ch.7 says a 200 ms fade would take "roughly 400 ms" at 120 Hz; that does not follow from the code (more draws with the same step should shorten it), so treat that sentence as unreliable.
- [SRC] messenger/utils/Choreographer60FpsContent.java (new since the book's tag): wrapper over Choreographer that delivers callbacks at a stable ~60 fps regardless of display refresh (TARGET_FPS 60, groups of callbacks at the same fps share one tick). Used by ChatMessageCell.java:21232 (15 fps) and :6464, ChatActivity.java:4322.
- [SRC] ui/LaunchActivity.java:860 checkFrameMetrics + messenger/utils/FrameMetricsOverlayView.java (422 lines): Telegram ships an in-app frame-metrics overlay gated by SharedConfig.frameMetricsEnabled.

## 4. Compose mapping, technique by technique (official docs first)

Doc "last updated" dates are the stamps on the pages when fetched (2026-10-16 unless stated).

M1. Time-based animated value read at draw time (T1) -> Animatable / animate*AsState read inside graphicsLayer {} or drawBehind {}
- https://developer.android.com/develop/ui/compose/animation/value-based (2026-10-16): Animatable holds one value, animateTo / snapTo / animateDecay are suspend functions; changing target mid-run cancels and restarts from the current value AND velocity; animate*AsState does the same and recomposes its reader each frame.
- https://developer.android.com/develop/ui/compose/animation/quick-guide (2026-10-16): use animateFloatAsState with graphicsLayer { alpha } for fades, animateColorAsState with drawBehind for animated colour, animateIntOffsetAsState with Modifier.offset {} for position; "prefer lambda-based modifiers or graphicsLayer, which runs in the draw phase".
- https://developer.android.com/develop/ui/compose/phases (2026-09-22): a state read in the draw phase re-runs only draw; in layout re-runs layout then draw; in composition can recompose. Deferring reads via lambda modifiers (Modifier.offset { }) skips composition. The page does not name graphicsLayer lambdas; the graphics-modifiers page does (M3).
- https://developer.android.com/develop/ui/compose/performance/bestpractices (2026-09-22): defer reads with lambdas, derivedStateOf for thresholds, avoid backwards writes, stable lazy-list keys, remember expensive results, baseline profiles linked, release-mode caveat appears on the lists page.
- Difference to Telegram's AnimatedFloat: Telegram keeps value only on retarget (T1); Compose Animatable keeps value and velocity.

M2. Spring physics (T9) -> spring(dampingRatio, stiffness)
- https://developer.android.com/develop/ui/compose/animation/customize (2026-10-16): spring, tween, keyframes, snap; springs keep velocity continuous on interruption and are the default for animate*AsState and updateTransition; tween does not interrupt as smoothly; page recommends springs for user-driven points.
- Constants (read at https://composables.com/jetpack-compose/androidx.compose.animation/animation-core/objects/Spring, a mirror of the AndroidX source): StiffnessHigh 10000, Medium 1500, MediumLow 400 (default for enter/exit transitions), Low 200, VeryLow 50; DampingRatioHighBouncy 0.2, MediumBouncy 0.5, LowBouncy 0.75, NoBouncy 1.0; DefaultDisplacementThreshold 0.01. spring() defaults: dampingRatio = NoBouncy (1.0), stiffness = Medium (1500), visibilityThreshold null (https://composables.com/jetpack-compose/androidx.compose.animation/animation-core/functions/spring).
- Same constants and the same oscillator model exist in androidx.dynamicanimation (the library Telegram uses): read in AOSP source https://android.googlesource.com/platform/frameworks/support/+/refs/heads/androidx-main/dynamicanimation/dynamicanimation/src/main/java/androidx/dynamicanimation/animation/SpringForce.java : the same eight constants; default there is damping 0.5 and stiffness 1500. Compose's SpringSimulation (AOSP, compose/animation/animation-core/.../SpringSimulation.kt) is a damped harmonic oscillator with natural frequency = sqrt(stiffness). So Telegram's explicit damping/stiffness pairs (T9) carry over numerically as spring(dampingRatio, stiffness); the unstated-default differs: View default damping 0.5, Compose spring() default 1.0 [FACT from both sources; that the two integrators give identical motion is a GUESS, same equations, not tested].
- https://developer.android.com/develop/ui/views/animations/spring-animation (2026-05-28) says Compose is now the recommended toolkit with its own spring AnimationSpec.

M3. Offscreen caching, layers, alpha (T10) -> graphicsLayer + CompositingStrategy
- https://developer.android.com/develop/ui/compose/graphics/draw/modifiers (2026-10-16): graphicsLayer records content separately and the renderer replays it without re-running your draw code; supports scale, translation, rotation, pivot (default 0.5, 0.5), clip/shape, alpha, compositingStrategy, and from 1.12.0-alpha01 LayerOutsets. It affects only the draw phase (layout size unchanged). Use the lambda form for animated values: skips recomposition and the draw lambda does not re-run.
- CompositingStrategy (added 1.4.0-alpha02): Auto = offscreen buffer when alpha < 1 or a RenderEffect is set (overscroll also forces one); Offscreen = always rasterise to a buffer first, sized to bounds (use for BlendMode masking or to cache complex drawing; costs memory; clips to bounds); ModulateAlpha = apply alpha per draw command, no buffer, cheaper, but overlapping content shows seams. A RenderEffect always forces an offscreen pass.
- rememberGraphicsLayer + record {} + drawLayer / toImageBitmap from 1.7.0-alpha07 (record a composable once, replay it).
- View-system precedent that Telegram's 43 LAYER_TYPE_HARDWARE files follow: https://developer.android.com/develop/ui/views/graphics/hardware-accel (2024-02-22): a hardware layer caches the view as a GPU texture; alpha, translation, scale, rotation, pivot changes then only recomposite and do not redraw; layers use video memory so reset to NONE when the animation ends.
- Blur (T10): Modifier.blur is Android 12+ only and ignored below; it renders into its own layer clipped to bounds so leave blur-radius padding (read on the composables.com mirror https://composables.com/jetpack-compose/androidx.compose.ui/ui/modifiers/blur, not the official page). Compose UI 1.13.0-alpha03 notes mention a progressive Modifier.blur { } overload (source: https://developer.android.com/jetpack/androidx/releases/compose-ui). AGSL/RuntimeShader is the route for shader effects like vaporize; I did not fetch an official Compose AGSL page.

M4. Custom-drawn rows with precomputed text (T2) -> Modifier.drawWithCache, Canvas, TextMeasurer / TextLayoutResult
- https://developer.android.com/develop/ui/compose/graphics/draw/modifiers (2026-10-16): drawWithCache runs a setup block once and rebuilds only when the draw size or a state read in setup changes; use it only when objects are allocated at draw time (otherwise extra lambdas add allocations); cached objects can be Brush, Shader, Path.
- TextMeasurer / drawText (only reached through mirrors: https://composables.com/docs/androidx.compose.ui/ui-text/classes/TextMeasurer and the drawText samples): TextMeasurer has an internal LRU cache of layout input/output; when only draw attributes change (for example colour animation) the sample sets cacheSize = 0 and computes the TextLayoutResult once in drawWithCache; another sample measures in a layout modifier and stores the result in snapshot state; the comment says text layout can happen any time before draw, including on a background thread.
- Lists: contentType (since Compose 1.2) lets compositions be reused only between items of the same type; keys must be stable (https://developer.android.com/develop/ui/compose/lists, 2026-10-16). Page says to measure lazy layouts only in release builds with R8, and to avoid zero-pixel items.
- No official doc found that says "flatten a list row into one custom-drawn node"; Telegram's single-view cell (T2) has no official Compose counterpart text. [GUESS] drawWithCache + TextMeasurer is the closest documented mechanism.

M5. Item animator opt-in per update (T3) -> Modifier.animateItem()
- https://developer.android.com/develop/ui/compose/lists (2026-10-16): put Modifier.animateItem() on the item content with stable keys; optional fadeInSpec, fadeOutSpec, placementSpec. The page's sample (not the defaults, defaults are not stated on the page) uses fadeIn tween 250 ms, fadeOut tween 100 ms, placement spring(StiffnessLow, DampingRatioMediumBouncy).
- Release notes https://developer.android.com/jetpack/androidx/releases/compose-foundation : animateItem introduced 1.7.0-alpha07 (2024-04-17) for grids, stable 1.7.0 (2024-09-04) for LazyColumn/LazyRow, replacing the deprecated animateItemPlacement; it covers fade in, fade out and reorder. 1.13.0-alpha02 computes visible item bounds before placement animations in list and grid measure; a skip-placement-animation fix flag was removed in 1.13.0-alpha01.
- Telegram's pattern (null animator unless the update is animated and the screen is open) maps to: apply animateItem only where an item should animate [GUESS, no doc states this pattern]. Roadmap https://developer.android.com/jetpack/androidx/compose-roadmap (April 2026, footer 2026-05-15) still lists "LazyList Item Animations" as a roadmap item.
- Related but different from T4 (Telegram pauses heavy work during an animation; Compose prefetches ahead of scroll and has no documented "pause work during transition" switch): lazy list prefetch notes: nested prefetch of the first 2 items 1.7.0-alpha08 (2024-05-01); LazyLayoutCacheWindow introduced for grids 1.9.0-alpha01 (2025-04-23); default cache window sized from average visible item size, clamped to 10%-50% of the viewport ahead (API reference mirrors); pausable composition in prefetch default-on in 1.10.0-alpha05 (2025-10-08) and in the Dec 2025 blog, but disabled by default again in compose-foundation 1.10.6 (2026-03-25) and the flag removed in 1.13.0-alpha03 (the two statements conflict as sequence of releases; both are in the release notes) [flag].

M6. Shared-element and container transitions (message send animation in the contest brief, T12) -> SharedTransitionLayout, sharedElement, sharedBounds, Modifier.animateBounds
- https://developer.android.com/develop/ui/compose/animation/shared-elements (2026-10-16) and /customize and /navigation (2026-10-16): SharedTransitionLayout provides SharedTransitionScope; sharedElement for same content, sharedBounds for different content (preferred for Text whose weight/colour changes); needs an AnimatedVisibilityScope from AnimatedContent, AnimatedVisibility or NavHost/NavDisplay; matched elements are drawn in a scope overlay while active (renderInSharedTransitionScopeOverlay(zIndexInOverlay) keeps bars on top); ResizeMode ScaleToBounds (graphical scale, no re-layout, recommended for Text) vs RemeasureToBounds (re-measures every frame); skipToLookaheadSize / skipToLookaheadPosition; clipInOverlayDuringTransition; keys must be unique. Default bounds spring values are not stated on the pages.
- Limits stated on the page: no Views-Compose interop (including Dialog and ModalBottomSheet), ContentScale on shared images snaps, no shape morph.
- Release timeline from https://developer.android.com/jetpack/androidx/releases/compose-animation : experimental in 1.7.0 (2024-09-04); animateBounds added 1.8.0 (2025-04-23); shared transition APIs stable in 1.10.0 (2025-12-03) together with skipToLookaheadPosition, dynamic enable/disable, start-with-gesture-velocity, veil transitions (experimental); 1.11.0 (2026-04-22) shared-element map access faster, SeekableTransitionState off-thread fix, visual-debug lookahead APIs; 1.12.1 stable 2026-09-09; 1.13.0-beta01 2026-10-07.
- Modifier.animateBounds (search result summary of the reference, https://developer.android.com/reference/kotlin/androidx/compose/animation/animateBounds.modifier): needs a LookaheadScope, takes boundsTransform, ignores motion-frame (scroll) position changes unless animateMotionFrameOfReference = true; experimental at 1.8.0-rc01.

M7. Predictive back with a seekable transition (T11) -> SeekableTransitionState / Navigation / NavigationBackHandler
- SeekableTransitionState: added 1.6.0-alpha04 (2023-08-23); 1.7.0-alpha05 (2024-03-20) made seekTo() the seek call and added an instant snapTo(); fixes in 1.7.2, 1.8.1, 1.11.0 (compose-animation notes). Reference summary: seekTo moves a fraction toward a target state, animateTo animates to it, one instance serves one Transition only (search result of https://developer.android.com/reference/kotlin/androidx/compose/animation/core/SeekableTransitionState).
- Navigation Compose 2.8.0-alpha02 (2024-02-07) release note: in-app predictive back via the new SeekableTransitionState APIs, back gesture previews the previous destination with the custom Transition and then commit or cancel (https://developer.android.com/jetpack/androidx/releases/navigation). 2.8.0-alpha06 (2024-04-03): a flicked gesture now completes the custom transition instead of finishing instantly. 2.8.0 stable date not read.
- Official how-to: https://developer.android.com/develop/ui/compose/system/predictive-back-setup (2026-10-16): Android 15+ system animations on by default for apps using supported back APIs, Android 13-14 need the developer-option; activity 1.6.0+; navigation-compose 2.8.0+ gives a default cross-fade on back and popEnterTransition / popExitTransition to customise; Material3 1.3.0+ components animate automatically.
- Manual progress API: https://developer.android.com/develop/ui/compose/system/predictive-back-progress (2026-10-16) describes PredictiveBackHandler (activity 1.6.0+): a Flow of back events, progress 0..1, touchX/touchY, cancellation arrives as a CancellationException. Newer page https://developer.android.com/guide/navigation/navigation-event/handle-back (2026-09-22) uses NavigationBackHandler + rememberNavigationEventState; progress 0.0..1.0, swipeEdge EDGE_LEFT/EDGE_RIGHT, onBackCompleted / onBackCancelled; says use a nav library with built-in predictive back such as Navigation 3 instead of doing it by hand. A third-party Medium post says PredictiveBackHandler is deprecated in Compose Multiplatform 1.10.3 [CLAIM, search snippet only].
- Navigation 3 (https://developer.android.com/guide/navigation/navigation-3/animate-destinations, 2026-10-06): NavDisplay has transitionSpec (push), popTransitionSpec (back), predictivePopTransitionSpec (gesture; receives the swipe edge since 1.0.0-alpha07, 2025-08-13), overridable per entry via metadata keys; sharedTransitionScope parameter for shared elements. Release notes https://developer.android.com/jetpack/androidx/releases/navigation3 : 1.0.0 stable 2025-11-19; 1.1.0 stable 2026-04-08 adds shared elements between scenes; 1.2.0 stable 2026-09-23 adds NavigationBackHandler wiring and gestures that start mid forward-transition; 1.3.0-alpha01 2026-09-23 moves to DeferredAnimatedContent for the predictive handoff; 1.3.0-alpha02 2026-10-07.
- Compose animation 1.12.0-alpha03 (2026-05-19) added a mutableTransform parameter to AnimatedVisibility and AnimatedContent for manual property changes during a deferred (predictive back) transition (compose-animation notes, via summariser).
- Telegram's thresholds (T11): lazy start at 1.5% progress and remap to 0..1; Compose pages above do not state any dead-zone value.

M8. Frame rate / refresh rate and animation power (T5, T6)
- https://developer.android.com/develop/ui/views/animations/adaptive-refresh-rate (2026-02-26): Android 15 QPR1+ adaptive refresh rate (check Display.hasArrSupport()); views vote Normal (about 60 Hz) or High or a numeric rate; touch boost to High on ACTION_DOWN; flings lower rate as velocity drops (custom scrollables should set frameContentVelocity every frame, example 1000 px/s); window.isFrameRateBoostOnTouchEnabled, isFrameRatePowerSavingsBalanced; RecyclerView 1.4.0 and Core 1.15.0 needed for the scroll behaviour. Compose 1.9+: Modifier.preferredFrameRate(Float) and preferredFrameRate(FrameRateCategory) (page text once calls it requestedFrameRate; signatures say preferredFrameRate). Telegram's window-level preferredRefreshRate (T5) predates ARR.
- Animator duration scale: Compose reads the system scale through the MotionDurationScale coroutine context element; scale 0 finishes motion on the next frame (https://developer.android.com/reference/kotlin/androidx/compose/ui/MotionDurationScale via search result). The Kotlin Slack note that flings ignore the scale is third-party.
- Degradation by device class (T6) has no framework counterpart in the docs I read; the platform only exposes inputs (memory class, SoC model on API 31+, battery). [GUESS] an app-level flag object like Telegram's LiteMode would be app code.

M9. Measuring smoothness
- FrameTimingMetric (Macrobenchmark): frameOverrunMs (positive = missed deadline), frameDurationCpuMs, frameCount; API 31+; reported as P50/P90/P95/P99 (search result for https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics). Compose benchmarking guide https://android.googlesource.com/platform/frameworks/support/+/androidx-main/docs/performance/compose_benchmarking.md names a Pixel 6 reference device.
- Official statements on Compose scroll parity: Dec 2025 blog (https://android-developers.googleblog.com/2025/12/whats-new-in-jetpack-compose-december.html, 2025-12-03): Google internal scroll benchmarks match Views; roadmap page says scroll jank "on par with Views since Compose 1.9.0". No percentages published.

## 6. Contradictions and cautions

1. Book vs 13.0.2: book says screenRefreshRate stays at 60 on the image-fade path; 13.0.2 updates it from the display (T5). The 16-per-call main-thread fade step is still there.
2. Book says Choreographer is referenced only by ThanosEffect; 13.0.2 has 25 files including a 60 fps helper (T5).
3. Book counts: ChatMessageCell 24,903 vs 29,584 lines; vendored recyclerview 42 vs 39 files; AnimatedFloat 219 vs 231 lines; ChatListItemAnimator moved from androidx package to ui/recyclerview. Architecture claims held in every item I re-checked; native claims (T7) could not be re-checked.
4. Smoothness is not uniform: source 10 reports chat-list stutter on 120 Hz in 12.5.0; Telegram's own March 2026 era redesign post says code was rewritten for responsiveness, and no Telegram reply to the bug is on the page.
5. Telegram blog efficiency claims (energy, fewer resources) come with no numbers anywhere.
6. Pausable composition in lazy prefetch: Dec 2025 blog and 1.10.0-alpha05 say on by default; compose-foundation 1.10.6 notes (2026-03-25, read through the summariser) say disabled by default; 1.13.0-alpha03 removes the flag. Current default in 1.12.1 not determined.
7. WebFetch gave "spring default damping" answers from mixed sources: the authoritative values are the AOSP/mirror values in M2.
