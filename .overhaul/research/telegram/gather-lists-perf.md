## 1. Device performance tiers and LiteMode (what each tier turns off)

### 1.1 How the tier is measured (once per process)

- [FACT] messenger/SharedConfig.java:1612-1614: LOW=0, AVERAGE=1, HIGH=2. getDevicePerformanceClass() (:1625-1633) returns a debug override (pref overrideDevicePerformanceClass, set from the settings debug menu, :1193-1194) if set, else a cached value that is measured lazily on first call (:1629-1631). I saw no write of the measured value to prefs, only a pref READ of "devicePerformanceClass" at :636, so [GUESS] it is re-measured at each process start.
- [FACT] measureDevicePerformanceClass() (:1635-1697) inputs: SDK int, CPU core count (ConnectionsManager.CPU_COUNT), ActivityManager.getMemoryClass() (MB of Java heap per app), total RAM (ActivityManager.MemoryInfo.totalMem), and the MEAN over cores of /sys/devices/system/cpu/cpuN/cpufreq/cpuinfo_max_freq divided by 1000 and rounded up (so MHz, a mean, not the max). A core file that cannot be read is skipped; if none can be read, freq = -1.
- [FACT] LOW if any of: SDK<21; cores<=2; memoryClass<=100; (cores<=4 and freq known and freq<=1250 MHz); (cores<=4 and freq<=1600 and memoryClass<=128 and SDK<=21); (cores<=4 and freq<=1300 and memoryClass<=128 and SDK<=24); total RAM < 2 GiB (:1672-1680). On SDK>=31 an SoC deny list also forces LOW: the hash of Build.SOC_MODEL upper-cased is looked up in the int array LOW_SOC (:360-..., first entries are Exynos 850, 7872, 7880) (:1640-1647).
- [FACT] AVERAGE if not LOW and any of: cores<8; memoryClass<=160; (freq known and freq<=2055 MHz); (freq unknown and cores==8 and SDK<=23) (:1682-1688). Everything else is HIGH. So HIGH needs 8 cores AND memoryClass>160 AND mean max freq >2055 MHz.
- [CALC] The user's phone (Redmi Note 10 Pro Max, Snapdragon 732G; from my memory of the spec, not read from the device: 2 cores at 2.3 GHz and 6 at 1.8 GHz) gives a mean of (2*2300 + 6*1800)/8 = 1925 MHz, which is <= 2055, so it would measure AVERAGE if sysfs exposes those numbers. [GUESS] Real sysfs values and memoryClass on the custom ROM were not read (no adb allowed here).
- [FACT] Both Settings and Profile debug dialogs print "current" vs "measured" class and allow forcing a class (ui/SettingsActivity.java:1683, 1720-1725; ui/ProfileActivity.java:4914, 4951-4956).

## 2. Gating: pausing work while something moves or scrolls

### 2.1 NotificationCenter "animation in progress" lock (postpone, do not drop)

- [FACT] messenger/NotificationCenter.java. setAnimationInProgress(index, allowedIds[, stopHeavyOperations = true]) (:463-488) registers a lock with an allow-list of notification ids. While at least one lock exists, every notification that is not on EVERY active lock's allow-list is not delivered: it is appended to a delayedPosts list (:662-666) and replayed in its original order when the last lock is released (onAnimationFinish :526-545, runDelayedNotifications :547-557). A lock registered with allowedIds == null allows nothing (the allow-test loop breaks at that lock, :606-610).
- [FACT] Ids always delivered, even during a lock: startAllHeavyOperations, stopAllHeavyOperations, didReplacedPhotoInMemCache, closeChats, invalidateMotionBackground, needCheckSystemBarColors, messageReceivedByServer2 (:587).
- [FACT] Lock expiry: EXPIRE_NOTIFICATIONS_TIME = 5017 ms (:35). postNotificationName force-expires locks older than that (:595-602). A timer first fires 5017 ms after a lock is created (:483), then expires locks older than 1000 ms and re-arms for the youngest (:489-518, age test at :499). [CALC] so a forgotten lock lives at most about 5 s.
- [FACT] Replay: the delayed posts are copied to a temp list and posted one by one on the UI thread right after the last lock ends (:547-557). [GUESS] A burst of postponed events can land in one frame; I saw no batching or spreading of the replay.
- [FACT] doOnIdle(Runnable) (:919-925) runs a runnable at once, or queues it until all animation locks end.
- [FACT] AnimationNotificationsLocker (messenger/AnimationNotificationsLocker.java:1-47) wraps lock() and unlock() on the current-account center and the global center. 84 lines under T mention the class (grep count).
- [FACT] The chat list item animator uses a lock WITHOUT the heavy-ops stop (stopHeavyOperations = false) and a 19-id allow-list (ui/ChatActivity.java:1266-1287, lock calls :6494 and :6500): read-state events, pinned messages, connection state, userInfoDidLoad, theme/wallpaper changes, messageReceivedByServer2 and a few more pass; updateInterfaces is commented out of the list (:1277) so it is postponed. The lock is released from a posted runnable after the last animation ends (ChatActivity.java:6486-6552) rather than inside the animation callback.
- [FACT] updateInterfaces notifications are debounced by 250 ms only when BuildVars.DEBUG_VERSION (NotificationCenter.java:637-649, shouldDebounce :651-653, applied in postNotificationName at about :624).

### 3.2 One shared frame scheduler for decorative animations

- [FACT] messenger/utils/Choreographer60FpsContent.java (395 lines): a main-thread singleton that registers ONE Choreographer.FrameCallback. The constructor posts it (:228) and doFrame always re-posts itself (:245), with or without subscribers, so it ticks on every vsync once created. It accumulates vsync deltas in nanoseconds and dispatches a "tick" whenever the accumulator reaches FRAME_INTERVAL_NS = 1e9/60 (:36, :239-240), carrying the remainder (:240). So decorative work is capped at 60 ticks/s regardless of display rate (class comment :19-24). [CALC] on a 90 Hz panel (11.11 ms vsync) the pattern is a tick every second vsync then every vsync (22.2 ms, 16.7 ms alternating): average 60/s.
- [FACT] Subscribers choose an fps clamped to [1,60]. Subscribers with the same fps share a group and ALWAYS fire on the same tick, "so N animations at the same fps produce exactly one invalidate wave per period" (class comment :22-24, group comment :61-66). Each fps maps to a fixed 60-bit mask built from the nearest divisor of 60 plus leap frames centred in the cycle (buildFrameMasks :312, buildFrameMask :324-381); the schedule depends only on the fps, never on who subscribed (:316-321 comment).
- [FACT] API: addFrameCallback(Runnable | FrameCallback, fps), addFrameCallbackOnce, post (one-shot), postInvalidateView, postInvalidateDrawable (60 fps list), postInvalidateDrawable30fps (API :106, dispatched on every second tick, :289-293).
