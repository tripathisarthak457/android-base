## 1. Page stack: ActionBarLayout (push, pop, swipe-back, predictive back)

### 1.1 Structure that makes it cheap
- [FACT] ABL is a FrameLayout holding two page containers (containerView = top page, containerViewBack = page being revealed or discarded) plus sheetContainer and, for the main layout, a bottom-tabs strip (ABL:743-775, 729-741). The two containers are swapped by reference on push (ABL:2076-2078), on pop (ABL:2571-2573) and at the end of a committed swipe (ABL:1306-1309); nothing is re-inflated.
- [FACT] A page is just fragment.fragmentView (plus the fragment's ActionBar) added to a container. The fragment object keeps its fragmentView after it is removed from the tree; going back re-adds the same view and only calls performCreateView when fragmentView is null (ABL:2576-2596, 1366-1379). So a page below the top keeps its view tree and state; it is only detached.
- [FACT] After a push finishes, the page below is detached from the tree (presentFragmentInternalRemoveOld, ABL:1768-1805, called from the open-end runnable at ABL:2191) using removeViewInLayout (ABL:1785, 1799, 1336, 1342), i.e. without scheduling a new layout pass. Only one page is in the view tree at rest; two are attached during a transition.
- [FACT] hasOverlappingRendering: ABL returns false (ABL:3308-3311); DrawerLayoutContainer returns false (AB/DrawerLayoutContainer.java:150-152); the inner LayoutContainer returns true only on SDK 28+ (ABL:250-256).
- [FW] A View with alpha < 1 and hasOverlappingRendering()==true is rendered through an offscreen layer; with false the alpha is applied per draw op. Not stated in this source.
- [FACT] Input is blocked during animations: ABL.onInterceptTouchEvent returns true while animationInProgress or checkTransitionAnimation() (ABL:1039-1042); DrawerLayoutContainer.onInterceptTouchEvent returns parentActionBarLayout.checkTransitionAnimation() (DrawerLayoutContainer.java:59-61); LayoutContainer.dispatchTouchEvent drops DOWN events in preview-transition mode (ABL:418-421). Watchdog: checkTransitionAnimation force-finishes a transition older than 1500 ms (ABL:1747-1749).

### 1.2 Push and pop with the toolbar or back button: a hand-rolled frame loop, not a ValueAnimator
- [FACT] presentFragment (ABL:1944-2307): fragment.onFragmentCreate (1952), performCreateView (2004), page added to containerViewBack (2018), fragmentsStack.add (2066), fragment.onResume (2069), containers swapped (2076-2078), the new top container starts at alpha 0, translationX 48 (a plain pixel literal, not dp, ABL:2216-2225), then startLayoutAnimation(open) (ABL:2284). Animation only if pref "view_animations" (default true) or preview (ABL:1997).
- [FACT] startLayoutAnimation (ABL:1807-1917): each tick is a Runnable posted with AndroidUtilities.runOnUIThread that re-posts itself until progress reaches 1 (ABL:1812-1916). Per tick: dt = now - last frame in ms; on the very first tick a dt over 40 ms is reset to 0; otherwise dt is clamped to at most 18 ms (ABL:1822-1829). progress += dt / duration, duration = 150 ms (190 ms for the preview-open case) (ABL:1830-1831). Interpolator: DecelerateInterpolator(1.5) (ABL:614, 1873).
  - Open: top container alpha = interpolated (clamped 0..1), translationX = dp(48) * (1 - interpolated) (ABL:1876-1892). The page underneath does not move.
  - Close (button or API pop): the page being closed (containerViewBack after the swap at ABL:2571) goes alpha 1 -> 0 and translationX 0 -> dp(48) (ABL:1895-1907). The page revealed beneath is static.
  - [CALC] The 18 ms clamp means a hitch costs at most 18 ms of animation progress per tick, so a 150 ms animation needs at least 150/18, about 9 ticks, even if frames are dropped; it can run longer in wall time but never jumps over its last frames. The first-tick reset (dt=0) avoids burning progress on the frame that included view creation and layout.
  - [FACT] Per tick it also calls newFragment/oldFragment.onTransitionAnimationProgress (ABL:1835-1840) and blends the navigation bar colour with ratio min(1, 4 * progress) (ABL:1850-1864), so the colour is final after the first quarter.
- [FACT] No setLayerType call exists on this path. The only setLayerType(HARDWARE) in ABL is in prepareForMoving for the swipe (ABL:1404); every other call is LAYER_TYPE_NONE (ABL:1354, 1421, 1496, 1508). A grep for LAYER_TYPE in ABL returns only those lines.
- [FACT] Waiting for readiness before starting: (a) if the new fragment says needDelayOpenAnimation() the slide does not start until the fragment calls resumeDelayedFragmentAnimation() (ABL:1920-1928) or 200 ms pass (ABL:2270-2282); (b) if the keyboard is up in either container, the start waits 250 ms (or until a layout shows the keyboard closed, ABL:396-400, 2230-2269); on close the keyboard wait is 200 ms (ABL:2666-2676). Fragments overriding needDelayOpenAnimation: ChatActivity (T/ui/ChatActivity.java:27141-27148, returns firstLoading, except false when the page below is a ChatActivity with the keyboard visible), ProfileActivity (T/ui/ProfileActivity.java:9534-9539, true when playProfileAnimation==0), plus CacheControlActivity:786, CalendarActivity:1500, CallLogActivity:1504, ChatUsersActivity:2374, ManageLinksActivity:1754 (bodies of these five not read).
- [FACT] Custom per-fragment transitions: a fragment may return its own AnimatorSet from onCustomTransitionAnimation(isOpen, callback) (AB/BaseFragment.java:810-812, used at ABL:2213 and ABL:2662). Overridden in ChatActivity:43248, ProfileActivity:9899, IntroActivity:550, LoginActivity:8379, iv/RichEditor:181, Wallet/WalletSendEnterAmount:1913 (see section 3 for the first two).
- [FACT] Tablet "layers" mode (useAlphaAnimations, stack size 1): the whole ABL animates alpha 0 -> 1 and scale 0.9 -> 1 with EASE_OUT_QUINT, 200 ms (ABL:2142-2177); close is alpha 1 -> 0, scale 1 -> 0.9, AccelerateDecelerate, 200 ms (ABL:2694-2730).
- [FACT] "Preview" (long-press peek of a chat) uses the same loop with OvershootInterpolator(1.02) on open (ABL:615, 1868) and EASE_OUT_QUINT on close (ABL:1870): open scale = 0.7 + 0.3*interp, alpha = interp, with a menu translationY dp(40)*(1-interp); close scale = 0.9 + 0.1*(1-interp) (ABL:1878-1900). The previewed page is clipped by an outline with 29 dp (chat) or 24/12 dp corners, elevation dp(4), spot and ambient shadow colour 0xB0000000 (ABL:2083-2118). Pulling up more than dp(60) expands it with a 1 -> 1.05 -> 1 scale pulse, 200 ms, cubic-bezier(0.42, 0, 0.58, 1), plus a KEYBOARD_TAP haptic (ABL:2479-2481, 2506-2522).

### 1.3 What is drawn while the front page slides (ABL.drawChild, ABL:1084-1217)
- [FACT] The front container is moved by its own translationX (a View property); setInnerTranslationX(value) only stores the value and calls invalidate() (ABL:956-960). drawChild reads innerTranslationX to derive clip, scrim and shadow for both containers each frame.
- [FACT] When no transition animation is running, each page is clipped to its visible strip with clipRect: back page to the left of the front page's edge (+1 dp), front page from its edge to the right (ABL:1100-1103, 1170-1173). The clip is skipped while transitionAnimationInProgress or animationInProgress is true, i.e. during a button push/pop and during the settle animation after a swipe release; it is applied while the finger is tracking (ABL:1171, isTransitionAnimationInProgress at ABL:1764-1766).
- [FACT] Scrim on the page beneath: black, alpha = 120 * clamp(widthOffset / width, 0, 0.8) (so at most 96 of 255), drawn as one rect over the visible strip (ABL:1204-1211). widthOffset = width - translationX.
- [FACT] Edge shadow: the layer_shadow drawable is drawn at the front page's left edge with alpha = clamp(255 * widthOffset / dp(20), 0, 255), but only when SDK < 31 or the layout is a sheet (ABL:1180-1202).
- [FACT] On SDK 31+ (and not a sheet) the shadow drawable is not drawn; instead, while the front page is offset, ABL reads the device's rounded display corners from WindowInsets (RoundedCorner, 4 corners) and clips the front page with a rounded-rect Path using those radii (ABL:1111-1155). The right-layout variant fades the left radii in over dp(12) (ABL:1145-1151).
- [FACT] The header shadow under the ActionBar is a drawable drawn once per page after the page's child draw, alpha from ActionBar.getShadowAlpha (ABL:179-221); SharedConfig.drawActionBarShadow gates the drawHeaderShadow path (ABL:944-954).

### 1.4 Swipe-back gesture (finger driven), classic path (ABL.onTouchEvent, ABL:1412-1519)
- [FACT] Where it starts: anywhere on the page, not an edge zone. ACTION_DOWN records the start point if the top fragment's isSwipeBackEnabled(ev) is true (default true, AB/BaseFragment.java:304-306; ABL:1415-1431). Requires stack size > 1, no sheet showing (ABL:550-552), no action mode, no running animation, no predictive back running (ABL:1413-1414).
- [FACT] Recognition on MOVE (ABL:1439-1446): dx (rightward only, clamped at 0) >= getPixelsInCM(0.4, true) [0.4 / 2.54 * xdpi pixels, AndroidUtilities.java:2902-2904] AND dx/3 > |dy| (so the finger is within about 18.4 degrees of horizontal [CALC: atan(1/3)]) AND fragment.canBeginSlide() AND findScrollingChild finds no child under the finger that canScrollHorizontally(-1) (ABL:3351-3371, a recursive hit-test). ABL.onInterceptTouchEvent returns the result of this onTouchEvent, so ABL takes over the touch stream once tracking starts (ABL:1039-1042).
- [FACT] Fling shortcut: on UP, if tracking never started but velX >= 3500 px/s (VelocityTracker.computeCurrentVelocity(1000)), velX > |velY| and canBeginSlide, it enters moving mode and finishes immediately (ABL:1465-1484).
- [FACT] What is built at the moment tracking starts (prepareForMoving, ABL:1358-1409): the previous fragment's view is created if missing (1366-1373), moved into containerViewBack with MATCH_PARENT params, its ActionBar added, fragment.onResume() called (1399), and containerView.setLayerType(LAYER_TYPE_HARDWARE) is applied to the TOP page only (1404); prepareFragmentToSlide(true/false, beginSlide=true) hooks on both fragments (1406-1408). The soft keyboard is hidden and fragment.onBeginSlide() is called on the first tracked move (ABL:1448-1455); BaseFragment.onBeginSlide dismisses a visible dialog and pauses the ActionBar (BaseFragment:727-738). So nothing page-sized is built before the 0.4 cm threshold; the layer is created only after it.
- [FACT] What follows the finger (classic): containerView.setTranslationX(dx) and setInnerTranslationX(dx), 1:1 (ABL:1459-1462). ABL itself never moves the page beneath (no view translation on containerViewBack, no layer on it); it only gets the scrim from 1.3 and the onSlideProgress/prepareFragmentToSlide callbacks (ABL:968-970, 1406-1408). Only DialogsActivity, TopicsFragment and MainTabsActivity override onSlideProgress (grep over T/ui), and they draw their own parallax (section 4.1). In ABL.setInnerTranslationX the previous fragment gets onSlideProgress(false, value/width) and the nav-bar colour is blended with ratio clamp(2*progress, 0, 1) (ABL:961-979).
- [FACT] Release decision (ABL:1485-1490): cancel when containerView.getX() < width/3 AND NOT (velX >= 3500 AND |velX| >= |velY|); i.e. commit when the page is at least a third across, or on a rightward fling >= 3500 px/s that is mostly horizontal.
- [FACT] End animation (animateBackEndAnimation, ABL:1597-1669): an AnimatorSet with two ObjectAnimators, containerView TRANSLATION_X and the "innerTranslationX" property, same duration, no interpolator set on the classic path (so the framework default applies). Commit: target = width; duration = max(200 / width * remainingDistance, 50) ms. Cancel: target = 0; duration = max(320 / width * x, 120) ms (ABL:1606-1630). [CALC] a full-width commit is 200 ms; a cancel from 1/3 width computes to about 107 ms, so the 120 ms floor applies.
- [FACT] The release velocity is used only for the commit/cancel decision; it is not passed to the animator, and duration depends only on the remaining distance (no spring, no velocity hand-off) in this layout (ABL:1597-1630).
- [FACT] End of swipe (onSlideAnimationEnd, ABL:1291-1356): on commit the top fragment is paused, destroyed and removed from the stack (1297-1304), containers swapped (1306-1310), previous fragment onResume + onBecomeFullyVisible (1318-1320). On cancel the revealed page's view is detached again with removeViewInLayout (1325-1346). Both: containerViewBack made INVISIBLE, translations reset, setLayerType(NONE) on containerView (1349-1355), so the hardware layer lives exactly for the gesture.
- [FACT] Fragments can replace the slide: shouldOverrideSlideTransition and getCustomSlideTransition (BaseFragment:977-983) are consulted for both pages at release and the returned Animator is played together with (or instead of) the default (ABL:1604-1643).

### 1.5 Android predictive back (system gesture), API 34+
- [FACT] Manifest: android:enableOnBackInvokedCallback="true" (AndroidManifest.xml:112). LaunchActivity registers an OnBackAnimationCallback at PRIORITY_DEFAULT on SDK >= 34 and a plain OnBackInvokedCallback (no progress) on SDK 33 (T/ui/LaunchActivity.java:738-851; SDK 34 block 738-828, SDK 33 block 829-851). Tablets skip the animation path (LaunchActivity:755, 776, 803, 818).
- [FACT] Lazy start: the layout's onBackStarted is not called at the system's onBackStarted; it is called the first time progress exceeds 0.015 (LAZY_START), and progress is then remapped to max(0, p - 0.015) / (1 - 0.015) (LaunchActivity:787-806). While it runs an AnimationNotificationsLocker holds the NotificationCenter in "animation in progress" (LaunchActivity:741, 781, unlock at 751 and 814; see 2.1).
- [FACT] ABL.onBackStarted (ABL:1526-1566) reuses the same prepareForMoving, so the same hardware layer and previous-page attach; it records which half of the screen the touch began in (predictiveBackLeft = touchX < displaySize.x/2) and the touch Y (ABL:1558-1559).
- [FACT] onBackProgress (ABL:1568-1574): dx = dp(56) * StandardDecelerate(t) (CubicBezierInterpolator.StandardDecelerate), written to containerView translationX and innerTranslationX. So the visible displacement saturates at 56 dp, not the full width.
- [FACT] In drawChild when predictive progress > 0 (newBackTransitions(), ABL:1591-1593): the front page is scaled about a pivot x = (left edge + dp(82)) or (right edge - dp(82)) depending on which side the touch started, pivot y = the touch Y; scale = lerp(1.00, lerp(0.90, 0.85, 1 - containerView.alpha), clamp01(translationX / dp(56))) so 1.0 -> 0.90 over the 56 dp (ABL:1118-1133). The page beneath is not clipped to a strip in this mode (ABL:1163-1165), and the front page is still clipped to rounded display corners on SDK 31+ (ABL:1136-1155). A canvas translate by -dx compensates the view translation (ABL:1123-1131). [CALC] The else branch at ABL:1121 (scale = 1 - min(0.25, 0.05*tx/dp(56))) sits inside newBackTransitions(), which requires predictiveBackInProgress, so it cannot run.
- [FACT] setInnerTranslationX uses progress = clamp01(value / (6 * dp(56))) in predictive mode instead of value/width (ABL:963-967). A touch-tracking variant exists too: containerView translation = dx/width * 5*dp(56) when newBackTransitions() holds during touch tracking (ABL:1456-1458).
- [FACT] Release in predictive mode (animateBackEndAnimation with the predictive flag): commit target = width + dp(56), duration = max(200/width*dist, 380) ms; cancel duration = max(320/width*x, 320) ms; both with EASE_OUT_QUINT on the AnimatorSet (ABL:1606-1630). Commit versus cancel is the system's decision (onBackInvoked vs onBackCancelled, ABL:1576-1589).

## 2. Work held back while something moves (the main "keep the animation cheap" mechanism)

### 2.1 NotificationCenter animation gate (T/messenger/NotificationCenter.java = NC)
- [FACT] setAnimationInProgress(oldIndex, allowedIds[, stopHeavyOperations=true]) (NC:463-486) registers a token (an increasing int) with an optional allow-list of notification ids and returns it; onAnimationFinish(token) (NC:526-545) removes it. While at least one token exists, postNotificationName does not deliver to observers: the post is queued in delayedPosts (NC:662-666) unless the id is in the built-in always-allowed set (startAllHeavyOperations, stopAllHeavyOperations, didReplacedPhotoInMemCache, closeChats, invalidateMotionBackground, needCheckSystemBarColors, messageReceivedByServer2; NC:587) or is in the allow-list of every active token (NC:589-613). When the last token ends, the queue is replayed in order (runDelayedNotifications, NC:547-558) and "doOnIdle" runnables queued meanwhile are re-posted to the UI thread (NC:560-566, doOnIdle NC:919-925: runs now if idle, else queues).
- [FACT] Safety: a token older than EXPIRE_NOTIFICATIONS_TIME = 5017 ms is expired the next time any notification is posted (NC:35, 595-600, 625-631); a watchdog runnable also re-checks (it expires tokens older than 1000 ms, NC:489-517, scheduled 5017 ms after registration at NC:481-483).
- [FACT] A second hook, addPostponeNotificationsCallback (NC:893-912, used at NC:667-673): ChatActivity registers one that holds back didReceiveNewMessages for its own dialog while firstLoading (ChatActivity:1298-1309, 2916, removal 3430).
- [FACT] Users: the helper class AnimationNotificationsLocker (T/messenger/AnimationNotificationsLocker.java:1-46: lock() takes one token on the current account's center and one on the global center, unlock() releases both) appears in 40 files (84 lines, grep). Examples read: BottomSheet open (BottomSheet.java:255, 1781, 1805), ActionBarPopupWindow close when requested (ActionBarPopupWindow.java:93, 1088-1090), AdjustPanLayoutHelper keyboard slide (AdjustPanLayoutHelper.java:77, 152, 225), theme switch animation (ABL:642, 3038-3043), predictive back (LaunchActivity:741, 781, 751, 814). ### 2.3 Device tiers and what each tier switches off
- [FACT] SharedConfig.measureDevicePerformanceClass (T/messenger/SharedConfig.java:1635-1693): inputs are SDK level, CPU count, ActivityManager memory class, an SoC-model blacklist (SDK 31+, LOW_SOC hashes), mean of /sys/devices/system/cpu/cpuN/cpufreq/cpuinfo_max_freq (MHz) and total RAM. LOW if SDK < 21, cpuCount <= 2, memoryClass <= 100, (cpuCount <= 4 and maxFreq <= 1250), (cpuCount <= 4, maxFreq <= 1600, memoryClass <= 128, SDK <= 21), (cpuCount <= 4, maxFreq <= 1300, memoryClass <= 128, SDK <= 24) or RAM < 2 GiB. AVERAGE if cpuCount < 8 or memoryClass <= 160 or maxFreq <= 2055 (or unknown freq with 8 CPUs and SDK <= 23). Otherwise HIGH. Result cached; overridable (overrideDevicePerformanceClass, SharedConfig:1625-1633).
  - [CALC] A phone with 8 cores, memory class > 160 and a mean max frequency above 2055 MHz is HIGH. The user's Redmi Note 10 Pro Max (Snapdragon 732G, 2x2.3 + 6x1.8 GHz [GUESS: from memory of the SoC, not read from any file]) would average about 1.9 GHz, so it would land in AVERAGE under these rules. Memory class of that device is unknown here.
- [FACT] LiteMode (T/messenger/LiteMode.java) turns the class into a bit mask of features (flags at LiteMode:23-50; presets PRESET_LOW/MEDIUM/HIGH at 52-85; loadPreference picks the preset by class unless the user saved a custom value, LiteMode:202-290). PRESET_LOW keeps only: animated-emoji premium variants (chat, keyboard, reactions), autoplay GIFs, "thanos" disintegration effect and particles.
